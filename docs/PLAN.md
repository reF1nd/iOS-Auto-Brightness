# 重构计划

状态：实现已落地，正在完成真机验收；当前实现及限制见 README、DEVICE 和 VALIDATION。以下保留设计依据与验收要求。首要目标：小米 17 Pro Max / Android 17 / HyperOS 4 / KernelSU。

## 1. 设备基线与功能清单

保留光线与距离传感器辅助、读取回退、平滑、回差、亮暗响应、用户学习、阳光模式、温度电量保护、配置热加载、日志与 WebUI。

先通过只读诊断确认目标设备的背光节点、亮度范围、传感器、温度数据，以及自动模式中拖动系统滑块所产生的状态变化。区分用户调整、系统自动变化和应用临时亮度。当前只有闭源参考包，核心需要重新实现。

## 2. 系统状态与核心分层

拆分传感器、系统状态、算法、设备控制、学习存储及服务管理。使用系统服务及状态监听替代截取用户 0 的设置 XML；必要时引入小型 Android 桥接进程，其可用接口需在目标 ROM 上验证。

处理当前用户、用户切换、亮度表示方式和状态不可用情形。不能把亮度设置发生变化直接判定为用户拖动。设备适配无法可靠识别输入时，不启用会产生错误样本的自动学习。

## 3. 可持久化学习

参考模块已有全局 `user_offset` 的保存和加载逻辑，因此重启失效的具体原因还需核对实际触发、写入及加载过程；不能直接断言原版没有持久化。新实现采用按照度分布的偏好点，记录稳定照度、用户目标、用户及面板标识、格式版本。

自动模式确认用户调整后及时尊重选择，稳定后确认学习样本。过滤遮挡、亮灭屏过渡、系统调光及模块自身写入。合并邻近样本，限定数量和影响范围，对学习曲线实施合理边界与单调性约束；温度、电量和设备上限优先。

学习数据保存在独立的 `/data/adb/ios_auto_brightness/`，不依赖模块目录或正常关机回调。确认学习后短暂防抖，通过临时文件、文件同步、原子替换和目录同步保存，并保留有效备份。区分待保存、已保存和失败；突然断电发生在确认保存前时，不承诺保留尚未提交的变化。

启动时先验证数据，取得有效环境照度后应用对应偏好。升级保留数据；旧版全局偏移只作为兼容偏移迁移，不推造历史样本。坏文件回退到有效备份并显式报告。

## 4. 控制逻辑修复

- 修复 0.5 lux 附近基础曲线断点，验证连续、单调及有限数值。
- 探测并验证背光节点，允许明确配置；多候选不盲选，固定亮度表只作为兼容配置。
- 优先采用不改节点权限的控制方式；必要时保存原权限、准确恢复并设计监督恢复流程。
- 验证与系统调光的控制权交接，避免高频覆盖争用。
- 动态发现温度节点，验证单位和时效；温度未知时禁止额外强光增强，不绕过系统保护。

## 5. 服务与生命周期

冲突检测失败立即停止启动，识别冲突模块是否启用。单实例锁配合进程身份核对，停止监督进程后再结束核心，避免仅凭 PID 误杀或卸载后被重启。

修改系统属性时记录原值并按需恢复。修复日志轮转、CPU 统计及配置校验；拒绝无效范围和非有限数。统一版本与安装流程，升级保留配置及学习数据。

## 6. WebUI

保留参数与日志功能，增加学习开关、样本查看、导入导出、清除、最后保存时间和恢复状态。基础曲线及学习曲线使用与核心一致的计算结果。

“保存并应用”需核心确认；展示实际设备接口、保护条件、降级原因及持久化错误。

## 7. 验收与交付

GitHub Actions 执行算法边界、学习插值、误学习过滤、用户切换、配置错误、存储失败、损坏恢复、异常结束及迁移测试，并进行 Android ARM64 构建和后续打包。

真机验证：在暗处、室内与强光环境分别调整；确认保存后重启服务和整机，在相近照度恢复对应偏好；验证关闭自动亮度后系统正常接管，异常时可靠降级，以及升级保留数据、长期运行和功耗。

交付完整源码、构建脚本、模块 ZIP、迁移说明和区分自动验证与真机验证的记录。先验证用户调整识别与控制权交接，再完成学习及持久化。
